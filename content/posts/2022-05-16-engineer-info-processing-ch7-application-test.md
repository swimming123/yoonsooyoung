2021년 3회, 2022년 1회 실기에서 테스트 파트는 "영문 키워드 박스를 주고 해당하는 것을 고르시오" 형태로 자주 나왔다.

## 애플리케이션 테스트

애플리케이션에 숨어 있는 결함을 찾아내는 일련의 행위와 절차.

- **Validation(확인)**: 고객의 요구를 만족하는지
- **Verification(검증)**: 기능을 정확히 수행하는지

### 기본 원리

- **완벽한 테스트는 불가능**: 결함이 하나도 없다고 증명할 수 없다.
- **파레토 법칙**: 전체 결함의 80%가 20%의 코드에서 발견된다.
- **살충제 패러독스**: 같은 테스트 케이스로 같은 테스트를 반복하면 더는 결함을 찾지 못한다.
- **테스팅은 정황에 의존**: SW 특징, 환경, 역량 등에 따라 결과가 달라진다.
- **오류-부재의 궤변**: 결함을 모두 없애도 요구사항을 만족하지 못하면 품질이 높다고 할 수 없다.
- **테스트와 위험은 반비례**: 테스트를 할수록 위험(risk)이 줄어든다.
- **테스트의 점진적 확대**: 작은 부분에서 점점 넓혀 간다(단위 → 통합 → 시스템).
- **테스트는 별도 팀이 수행**: 개발과 관계없는 팀이 해야 한다.

## 테스트 분류

**실행 여부에 따라**

- 정적 테스트: 실행하지 않음. 워크스루, 인스펙션, 코드 검사
- 동적 테스트: 프로그램을 실행함. 블랙박스 테스트, 화이트박스 테스트

**테스트 기반에 따라**

- 명세 기반: 요구사항 명세를 빠짐없이 테스트 케이스로 만들어 확인. 동등 분할, 경계값 분석(블랙박스)
- 구조 기반: 논리 흐름에 따라 테스트 케이스 작성. 구문 기반, 결정 기반, 조건 기반(화이트박스)
- 경험 기반: 테스터의 경험을 바탕으로 수행. 에러 추정, 체크리스트, 탐색적 테스팅

**시각에 따라**

- 검증(Verification): 개발자 시각. 명세대로 완성됐는지
- 확인(Validation): 사용자 시각. 요구사항대로 정상 동작하는지

**목적에 따라**

| 테스트 | 영문 | 내용 |
| --- | --- | --- |
| 회복 | Recovery | 결함을 주고 올바르게 복구되는지 |
| 안전 | Security | 보호 도구가 불법 침입을 막는지 |
| 강도 | Stress | 과부하를 줘도 정상적으로 실행되는지 |
| 성능 | Performance | 실시간 성능, 효율성, 응답 시간, 처리량 |
| 구조 | Structure | 내부 논리 경로, 소스 코드 복잡도 평가 |
| 회귀 | Regression | 수정한 코드에 새 결함이 없는지 |
| 병행 | Parallel | 변경된 SW와 기존 SW에 같은 데이터를 넣고 결과 비교 |

## 화이트박스 테스트

원시 코드의 모든 경로를 테스트하며, 모든 문장을 한 번 이상 실행한다.

- **기초 경로 검사(Base Path Testing)**
- **제어 구조 검사(Control Structure Testing)**
    - 조건 검사(Condition Testing): 모듈 안의 모든 논리적 조건을 테스트
    - 루프 검사(Loop Testing): 반복 구조에 초점
    - 데이터 흐름 검사(Data Flow Testing): 변수 정의와 사용 위치에 초점

**검증 기준**

- 문장 검증(Statement Coverage): 모든 구문이 한 번 이상 수행
- 분기 검증(Branch Coverage, Decision Coverage): 모든 조건문의 결과가 T/F인 경우가 각각 한 번 이상 수행
- 조건 검증(Condition Coverage): 개별 조건식의 결과가 T/F인 경우가 각각 한 번 이상 수행
- 분기/조건 검증(Branch/Condition Coverage): 분기 검증과 조건 검증을 모두 만족

## 블랙박스 테스트

각 기능이 완전히 작동하는지 입증하는 기능 테스트.

| 테스트 | 영문 | 내용 |
| --- | --- | --- |
| 동치 분할 검사 | Equivalence Partitioning | 옳은 자료와 옳지 않은 자료를 균등하게 넣어 결과 확인 |
| 경계값 분석 | Boundary Value Analysis | 입력 조건의 경계값을 테스트 케이스로 선정 |
| 원인-효과 그래프 | Cause-Effect Graphing | 입력 데이터 간 관계와 출력 영향을 분석해 테스트 케이스 선정 |
| 오류 예측 검사 | Error Guessing | 과거 경험으로 오류를 예측 |
| 비교 검사 | Comparison Testing | 여러 버전에 같은 테스트 자료를 넣어 같은 결과가 나오는지 |

## 개발 단계에 따른 테스트: V 모델

| 개발 단계 | 대응하는 테스트 |
| --- | --- |
| 요구사항(Requirements) | 인수 테스트(Acceptance) |
| 분석(Specification) | 시스템 테스트(System) |
| 설계(Design) | 통합 테스트(Integration) |
| 구현(Code) | 단위 테스트(Unit) |

- **단위 테스트**: 모듈, 컴포넌트 단위로 테스트
- **통합 테스트**: 단위 테스트가 끝난 모듈을 결합해 시스템으로 완성하는 과정에서 테스트
- **시스템 테스트**: 개발된 소프트웨어가 완벽하게 수행되는지, 기능·비기능 요구사항을 만족하는지
- **인수 테스트**: 요구사항을 충족하는지 사용자가 직접 테스트
    - 사용자 인수 테스트: 사용자가 시스템 사용의 적절성을 확인
    - 운영상의 인수 테스트: 시스템 인수 시 백업, 복원, 재난 복구, 사용자 관리 등 확인
    - 계약 인수 테스트: 계약 조건을 만족하는지
    - 규정 인수 테스트: 규정과 법규에 맞게 개발됐는지
    - 알파 테스트: 개발자 앞에서 사용자가 하는 테스트
    - 베타 테스트: 개발자 없이 사용자가 실제 업무 환경에서 하는 테스트

## 통합 테스트

단위 테스트가 끝난 모듈을 통합하면서 생기는 오류와 결함을 찾는 테스트.

- 점진적: 하향식, 상향식, 혼합식
- 비점진적: 빅뱅

**하향식 통합 테스트**: 상위 모듈에서 하위 모듈 방향으로 통합한다. 아직 없는 하위 모듈은 스텁(Stub)으로 대신하고, 깊이 우선 또는 넓이 우선으로 스텁을 실제 모듈로 바꿔 가며 통합할 때마다 테스트한다.

**상향식 통합 테스트**: 하위 모듈에서 상위 모듈 방향으로 통합한다. 하위 모듈을 클러스터(Cluster)로 묶고, 상위 모듈 대신 더미 모듈인 드라이버(Driver)를 만들어 클러스터 단위로 테스트한다.

**혼합식 통합 테스트**: 하위 수준은 상향식, 상위 수준은 하향식.

**회귀 테스팅(Regression Testing)**: 통합으로 변경된 모듈이나 컴포넌트에 새 오류가 없는지 확인.

## 테스트 프로세스와 결함 관리

- 테스트 프로세스: 테스트 계획 → 테스트 분석 → 테스트 케이스·시나리오 작성 → 테스팅 → 결과 리포팅 → 결함 추적·관리
- 결함 관리: 에러 발견 → 에러 등록 → 에러 분석 → 결함 확정 → 결함 할당 → 결함 조치 → 조치 검토 및 승인

## 테스트 케이스, 시나리오, 오라클

- **테스트 케이스**: 요구사항을 만족하는지 확인하려고 설계한 테스트 항목 명세서. 입력값, 실행 조건, 기대 결과 등으로 구성
- **테스트 시나리오**: 적용 순서에 따라 여러 테스트 케이스를 묶은 집합
- **테스트 오라클**: 결과가 올바른지 판단하려고 미리 정의한 참값을 대입해 비교하는 것. 특징은 제한된 검증, 수학적 기법, 자동화 기능

| 오라클 | 내용 |
| --- | --- |
| 참(True) | 모든 입력값에 대해 기대 결과를 제공, 모든 오류 검출 |
| 샘플링(Sampling) | 특정 몇몇 입력값에 대해서만 기대 결과 제공. 전수 테스트가 불가능할 때 |
| 추정(Heuristic) | 특정 입력값에 대한 결과를 주고, 나머지는 추정 |
| 일관성 검사(Consistent) | 변경이 있을 때 수행 전후 결과가 같은지 |

## 테스트 자동화 도구

- 정적 분석 도구: 실행하지 않고 코딩 표준, 스타일, 복잡도 분석
- 테스트 실행 도구: 스크립트 언어 사용. 데이터 주도 접근, 키워드 주도 접근
- 성능 테스트 도구: 가상의 사용자를 만들어 테스트
- 테스트 통제 도구: 테스트 계획·관리, 수행, 결함 관리
- 테스트 하네스 도구: 테스트가 실행될 환경을 시뮬레이션하는 코드와 데이터. 테스트 드라이버, 테스트 스텁, 테스트 슈트, 테스트 케이스, 테스트 스크립트, 목 오브젝트

## 애플리케이션 성능 분석

- 지표: 처리량(Throughput), 응답 시간(Response Time), 경과 시간(Turn Around Time), 자원 사용률(Resource Usage)
- 성능 테스트 도구: JMeter, LoadUI, OpenSTA (2022년 1회에는 JUnit이 나왔다)
- 시스템 모니터링 도구: Scouter, Zabbix

**복잡도**

- 시간 복잡도: 빅오(최악), 세타(평균), 오메가(최상)
- 순환 복잡도: 논리적인 복잡도 측정. 순환 복잡도 = 화살표(간선) 수 - 노드 수 + 2

**성능 개선**

- 소스 코드 최적화: 나쁜 코드(복잡한 로직, 스파게티 코드, 외계인 코드)를 없애고 누구나 쉽게 이해하는 클린 코드로 작성
- 클린 코드 원칙: 가독성, 단순성, 의존성 배제, 중복성 최소화, 추상화, 느슨한 결합
- 소스 코드 품질 분석 도구
    - 정적: PMD, Cppcheck, SonarQube, Checkstyle, CCM, Cobertura
    - 동적: Avalanche, Valgrind
