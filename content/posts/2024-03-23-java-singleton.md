## 싱글톤 패턴

자원과 관련된 객체를 무분별하게 만들지 못하도록 제어하는 패턴이다.

정수기를 쓰는 상황과 비슷하다. 여러 사람이 물을 마실 때 한 사람당 정수기를 한 대씩 복사해 주는 게 아니라, 정수기 한 대를 두고 한 사람이 쓰고 나면 다음 사람이 쓰는 모습이다.

- **규칙**: 생성자를 `private`으로 막고, static 영역에 객체를 딱 한 번만 만들어 돌려주는 메서드를 제공한다.
- **개념**: 그 메서드를 처음 호출할 때만 객체를 만들어 static 영역에 참조시켜 두고, 다시 호출하면 이미 만들어 둔 객체의 주소를 돌려준다.

```java
public class SingleTone {

    // 1. static 영역에 참조할 변수 선언 (private: 정보 은닉)
    private static SingleTone ref;

    // 2. 생성자를 private로 선언해서 외부에서 접근하지 못함
    private SingleTone() {
        System.out.println("생성자 호출!");
    }

    // 3. 싱글톤 객체를 얻는 메서드 제공 (캡슐화)
    public static SingleTone getInstance() {
        // 처음 getInstance()가 호출될 때 딱 한 번만 생성하고
        if (ref == null) {
            ref = new SingleTone();
        }
        // 그 뒤에는 이미 만든 ref 반환
        return ref;
    }

    // 4. 객체를 얻은 뒤 쓰는 메서드
    public void test() {
        System.out.println("메서드 테스트!!");
    }

    // 5. static 메서드도 제공
    public static void test2() {
        System.out.println("static 메서드 테스트!");
    }
}
```

- 생성자를 `private`으로 막아서 외부에서 `new`로 생성자를 호출할 수 없게 한다.
- 그래서 외부에서 마음대로 객체를 만들 수 없다.
- 대신 싱글톤이 제공하는 정적 메서드(`getInstance()`)로 간접적으로 객체를 얻는다.

## 싱글톤을 쓰는 이유

찾아본 내용을 정리하면 이렇다.

**장점**

- **인스턴스가 하나뿐**: 애플리케이션 전체에서 객체가 하나만 있다는 게 보장돼서 상태를 일관되게 유지하고 어디서든 접근할 수 있다.
- **메모리 절약**: 여러 번 호출해도 새로 만들지 않으니 메모리를 덜 쓰고, 생성·해제 비용도 줄어든다.
- **지연 초기화**: 실제로 쓰는 시점에 만들어서 초기 비용을 줄일 수 있다.

**단점**

- **결합도 증가**: 어디서든 접근할 수 있어서, 이 인스턴스에 기대는 코드가 많아지면 결합도가 높아진다.
- **테스트가 어려움**: 하나의 인스턴스를 공유하기 때문에 이 클래스에 의존하는 클래스를 따로 떼어 테스트하기 어렵다.
- **상태 관리가 어려움**: 싱글톤이 상태를 가지고 있으면 여기저기서 바뀌어 예상치 못한 동작이 생길 수 있다.
- **무분별한 사용**: 어디서든 쓸 수 있으니 사용을 통제하기 어렵고, 변경할 때 영향 범위가 커진다.

메모리 효율은 좋지만 그만큼 따라오는 문제도 있으니, 장단점을 따져서 상황에 맞게 써야 한다.
