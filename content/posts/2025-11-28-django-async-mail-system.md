이번에는 실제 서비스를 개발하면서 부딪혔던 **알림 인프라 구축기**를 정리해 보려고 한다.

서비스를 운영하다 보면 이런 얘기가 정말 많이 나온다.

- “서비스 상태가 좀 이상한데… 알림은 왜 안 와?”
- “사용자가 문의를 등록하면 바로 알려 줬으면 좋겠다”

그래서 헬스체크 이벤트나 문의 등록 이벤트가 발생하면 이걸 메시지 브로커로 흘려보내고, 백그라운드에서 워커가 메일을 비동기로 발송하는 구조를 만들게 됐다.

처음에는 “그냥 함수 하나 만들어서 바로 보내면 되지 않나?” 생각했는데, 막상 구축을 시작해보니 생각보다 고민할 게 많았다.
이번 글은 그 과정을 하나씩 정리해 본 기술 노트다.

---

## 1) 메시지 큐(Message Queue)란?

처음 메시지 큐를 공부할 때는 “그냥 큐잖아?”라고 생각했는데
막상 제대로 써보니까 역할이 확실히 다르다는 걸 느꼈다.

메시지 큐는 쉽게 말해서 **프로듀서(생산자)와 컨슈머(소비자)를 비동기로 분리하기 위한 장치**다.

웹 요청은 빠르게 응답해야 하는데
그 안에서 메일을 보내고, 외부 API를 호출하고, 이미지 처리까지 하면… 느려질 수밖에 없다.

그래서 무거운 작업은 전부 메시지 큐에 넣어두고 워커가 뒤에서 차근차근 처리하게 만든다.

이렇게 하면 좋은 점이 많다.

- **비동기 처리**: 웹 요청을 방해하지 않음
- **부하 분산**: 여러 워커를 병렬로 실행해 트래픽 분산
- **버퍼링**: 갑작스러운 이벤트 급증(spike)을 흡수
- **서비스 간 느슨한 결합**: 생산자/소비자가 서로 동시에 동작할 필요 없음
- **전달 보장 모델 선택**: 최소 한 번(at-least-once) / 최대 한 번(at-most-once) / 정확히 한 번(exactly-once)

메시지 큐는 단순 큐 외에도 Pub/Sub, 스트리밍, 이벤트 소싱 등 다양한 아키텍처 패턴의 기반이 된다.

## 2) Redis를 메시지 큐로 사용하기 vs RabbitMQ / Kafka 비교

Redis는 본래 인메모리 데이터 저장소이지만, 단순한 메시지 브로커로도 많이 활용된다.
다만 RabbitMQ나 Kafka처럼 메시징 전용으로 설계된 브로커와는 목적과 기능에서 차이가 있다.

### Redis (MQ로 사용할 때)

Redis는 원래 캐시/스토어 목적이었지만 작은 규모에서는 MQ 대용으로 많이 쓴다.

장점은 정말 빠르고 간단하다는 것.
설치도 쉽고 관리도 쉽고, 작은 서비스에는 딱이다.

다만 진짜 메시지 브로커는 아니라서 라우팅, 우선순위, DLQ 같은 기능은 부족하다.
운영하면서 메시지 유실 가능성도 신경 써야 한다.

**장점**

- 매우 빠른 성능(메모리 기반)
- 설치/운영이 쉬움
- 간단한 큐 패턴 구현에 적합
- 작은 규모의 백엔드 작업 큐에 잘 맞음

**단점**

- 장애 시 메시지 손실 가능 (AOF/RDB 설정으로 보완 가능하지만 관리 복잡)
- 고급 메시징 기능(라우팅, 우선순위, DLQ 등) 부족
- Streams를 쓰면 컨슈머 그룹·ACK 같은 기능이 생기지만, 그만큼 직접 관리할 것도 늘어남

### RabbitMQ (AMQP 기반 메시징)

메시징 전문 브로커답게 신뢰성 기능이 매우 튼튼하다.
라우팅(exchange), ACK, TTL 등등…

하지만 운영 난이도는 Redis보다 확실히 높다.
설정해야 할 옵션도 많고, 초기 진입 장벽이 있다.

**장점**

- 메시징을 위해 설계된 전통적 브로커
- ACK/재시도/TTL/우선순위/DLQ 등 신뢰성 기능이 매우 풍부
- 라우팅(exchange binding) 기능이 뛰어남

**단점**

- 운영과 튜닝 난이도가 Redis보다 높음
- 디스크 영속성을 켜면 성능은 다소 감소

### Kafka (분산 로그/스트리밍)

Kafka는 메시지 큐라기보다 “분산 로그”에 가깝다.
대용량 이벤트 스트리밍에 최적화돼 있다.

근데 단순히 ‘이메일 보내는 큐’ 용도로는… 오버스펙이다 ㅋㅋ

**장점**

- 대용량 이벤트 스트리밍, 로그 기반 처리, 이벤트 소싱에 최적화
- 메시지가 “소비되고 지워지는 큐”가 아니라 로그로 남아 여러 컨슈머가 소비 가능

**단점**

- 단순한 작업 큐 용도로는 오버스펙
- 운영 경험과 인프라 비용이 필요

### 선택 기준

- 작은 서비스: Redis
- 신뢰성/라우팅 중요: RabbitMQ
- 대규모 시스템/스트리밍: Kafka

우리 상황에서는 Redis면 충분했다.

## 3) Django에서 Celery가 하는 역할

Django에서 비동기 작업을 처리한다고 하면 대부분 **Celery**를 떠올린다.

나도 그랬다.

Celery는 **파이썬 기반 분산 작업 큐(Distributed Task Queue)** 로, Django에서 비동기 작업을 수행할 때 가장 널리 사용된다.

### Celery 구성 요소

- **브로커**: Redis, RabbitMQ 등
- **워커(Worker)**: 브로커에서 메시지를 꺼내 작업 처리
- **결과 백엔드(Optional)**: 작업 상태/결과 저장
- **Beat**: 정기 스케줄러 (cron 대체)

### Django에서 Celery의 장점

- 이메일 전송, 이미지 처리, 외부 API 호출 같은 무거운 작업을 비동기로 분리
- 재시도, 타임아웃, backoff, 체이닝, 그룹 작업 같은 고급 기능 제공
- Django 설정과 쉽게 통합되며, 대규모 서비스에서도 검증된 환경 제공

처음엔 “Celery 쓰면 편하겠다!” 싶었는데 아래에서 말하겠지만 이번 프로젝트에서는 최종적으로 사용하지 않았다.

## 4) 데몬(Daemon)과 워커(Worker)

이 부분은 내가 실제로 구축하면서 몇 번이고 헷갈렸던 개념이어서 따로 정리했다.

### 데몬(Daemon)

- 리눅스/유닉스에서 백그라운드에서 상시 실행되는 프로세스
- 터미널과 분리되어 서비스처럼 동작
- Windows에서는 “서비스(Service)”가 같은 개념
- systemd 서비스처럼 항상 떠 있는 형태

### 워커(Worker)

- 큐에서 작업 메시지를 꺼내 처리하는 역할
- 데몬처럼 지속적으로 실행될 수 있고, 여러 개가 병렬로 동작할 수 있음

즉, **워커는 역할**, **데몬은 실행 방식**이라는 관점으로 이해하면 된다.

## 5) Celery vs 직접 만든 워커 데몬

여기서 제일 고민했던 부분이다.

팀에서는 이런 의견이 있었다.

- “프로세스가 너무 많으면 운영이 복잡해진다”
- “Celery는 배워야 하는 게 많다”

게다가 우리 요구사항은 생각보다 단순해서 Celery의 고급 기능은 거의 쓰지 않을 것 같았다.

그래서 결론적으로 **커스텀 워커 데몬을 직접 구축하는 방향**을 택했다.

### A. Celery 사용 시 장단점

**장점**

- 재시도, 타임아웃, 체이닝 등 완성된 기능 제공 (신뢰성 굿)
- 브로커 지원 폭이 넓음
- 모니터링 도구(Flower) 등 성숙한 생태계
- 운영이 체계적이고 스케일링이 쉬움

**단점**

- 초기 설정 복잡
- 아주 단순한 요구에는 다소 과할 수 있음
- Celery 특유의 동작 모델에 맞춰야 하는 부분 존재

```text
사용자
  |
  v
Django 웹서버
  |
  |  (비동기 작업 요청)
  v
메시지 큐(MQ, 예: Redis)
  |
  v
Celery Worker
  |
  |  (SMTP / API 호출)
  v
메일 서버(SMTP 또는 외부 이메일 서비스)
```

### B. 직접 만든 워커(커스텀 데몬)의 장단점

**장점**

- 요구사항이 단순할 때 구현이 빠름
- 필요 없는 기능이 없어 가볍다
- 특정 도메인 로직을 완전히 원하는 대로 제어 가능

**단점**

- 재시도/ACK/중복 처리 등 신뢰성 기능을 직접 구현해야 함
- 스케일링·동시성 제어가 복잡해짐
- 모니터링·자동 재시작 등 운영 부담 증가

```text
사용자
  |
  v
Django 웹서버
  |
  |---(POST /send-email 요청)
  |
  |--- 작업 메시지 생성
  v
메시지 큐 (Redis / RabbitMQ / Kafka)
  |
  |--- 메시지 저장 & 전달
  |
  v
+---------------------------------+
| 워커 계층 (Worker)              |
|  - Custom Daemon                |
|  - 재시도 / 백오프 / 중복 확인  |
|  - 동시성 처리 (멀티 프로세스)  |
+---------------------------------+
  |
  |--- 실제 메일 발송(SMTP / API)
  v
메일 서버 (SMTP 서버 / SendGrid / Amazon SES 등)
  |
  v
수신자
```

길게 보면 Celery가 더 안정적이었겠지만, 이번에는 “지금 당장 빨리 구축해야 하는 상황”이라 가벼운 커스텀 워커가 더 맞았다.

- **소규모·단순한 시스템** → 커스텀 워커로 빠르게 시작 가능
- **신뢰성·운영성·확장성 필요한 서비스** → Celery(혹은 전문 MQ + 워커) 권장

## 6) 메일 발송 시스템에서 고려한 체크리스트

구축한 워커 데몬 기반 메일 시스템에서 중요하게 본 항목은 아래와 같다.

- **메시지 손실 방지** → MQ 또는 DB 기반 영속화
- **중복 전송 방지(Idempotency)** → 메일 ID 기반 체크
- **재시도/백오프 정책** → SMTP 오류 대비
- **스케일링 전략** → 워커 수 조정, 스파이크 대응
- **모니터링** → 큐 길이, 실패율, 소비 속도
- **운영 자동화** → Kubernetes 기반 auto-restart
- **배포 안정성** → 롤링 업데이트 시 중복 처리 방지

## 7) 결론

이번 프로젝트에서는 **Redis + 커스텀 워커 데몬** 조합으로 메일 발송 시스템을 구축했다.

서비스가 아직 작고 요구사항도 단순해서 이 방식이 가장 빠르고 운영 부담도 적었다.

하지만 장기적으로 트래픽이 늘어나거나 재시도가 더 복잡해지는 상황이 오면 Celery로 마이그레이션할 가능성이 크다.

메시지 큐 기반 구조는 알림 시스템뿐 아니라 이벤트 기반 아키텍처로 확장할 수 있는 기반이라, 이번 경험이 나중에 다른 서비스 설계할 때도 큰 도움이 될 것 같다.
