카테고리를 고르면 해당 목록을 보여 주는 리스트 페이지를 Vue + Django로 만들었다. 목록의 각 항목에는 태그가 `"이미지,음성,번역"`처럼 콤마로 이어진 문자열로 들어 있었는데, 화면에서는 태그를 하나씩 칩으로 보여 줘야 했다.

처음에는 응답을 받자마자 태그를 배열로 바꿔서 저장할까 했는데, 그러면 원본 데이터가 바뀐다. 여기서 **데이터 모델과 뷰 모델을 나누는** 개념을 정리하게 됐다.

## 데이터 모델 vs 뷰 모델

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| 데이터 모델 | 서버나 DB에서 내려온 원본 데이터. 변형하지 않는다. | 각 항목의 `tags: string` |
| 뷰 모델 | 화면에서 그리기 쉽게 바꾼 데이터. 화면 전용이다. | `tags.split(',')`로 나눈 배열 |

원칙은 두 가지다.

- 원본 데이터는 최대한 건드리지 않는다.
- 화면에 보여 줄 때만 필요한 가공을 한다.

## 왜 나눌까?

- **데이터 일관성**: 원본이 그대로라 다른 컴포넌트나 함수에서 그대로 다시 쓸 수 있고, 다른 로직과 부딪히지 않는다.
- **화면 최적화**: 화면마다 필요한 형태로 따로 가공할 수 있고, 화면이 바뀌어도 원본에는 영향이 없다.
- **타입 안정성**: 원본 타입과 가공된 타입이 명확하게 나뉜다.
- **유지보수**: API 스펙이 바뀌면 원본 쪽만 고치고, 화면 가공은 각 컴포넌트에서 맞추면 된다.

## 어디서 온 개념일까?

MVVM(Model-View-ViewModel) 패턴의 핵심 아이디어다. Vue도 사실상 MVVM 구조다.

- **Model**: 서버 API 응답 데이터
- **ViewModel**: 컴포넌트 안의 `computed`, `watch`, 메서드
- **View**: 템플릿

이번에 한 건 뷰 모델 계층에서 데이터를 가공해서 뷰에 넘긴 경우다.

## 실제로 적용하기

원본은 응답 그대로 저장한다.

```ts
interface Item {
  id: number
  name: string
  tags: string // "이미지,음성,번역"
}

const items = ref<Item[]>([])
items.value = res.data.items
```

간단하면 템플릿에서 바로 가공해도 된다.

```vue
<span v-for="tag in item.tags.split(',')" :key="tag">{{ tag }}</span>
```

여러 곳에서 쓰거나 조금 복잡해지면 `computed`로 뷰 모델을 만든다. 가공된 타입도 따로 정의해 두면 원본과 헷갈리지 않는다.

```ts
interface ItemView extends Omit<Item, 'tags'> {
  tags: string[]
}

const itemViews = computed<ItemView[]>(() =>
  items.value.map((item) => ({
    ...item,
    tags: item.tags ? item.tags.split(',').map((t) => t.trim()) : [],
  })),
)
```

## 정리

- 원본 데이터는 API 응답 그대로 유지한다.
- 화면에만 필요한 데이터는 `computed`, 메서드, 템플릿에서 가공한다.
- TypeScript를 쓴다면 원본과 가공 데이터의 타입을 따로 정의한다.
- 컴포넌트마다 책임을 나누면 유지보수가 편하다.

Vue뿐 아니라 React, Django, FastAPI에서도 똑같이 적용할 수 있고, API를 설계할 때도 "이건 원본, 이건 화면 전용"을 구분해서 생각할 수 있게 됐다.

> 데이터 모델과 뷰 모델은 구분하자. 원본은 유지하고, 화면에 필요한 건 화면에서 가공하자.
