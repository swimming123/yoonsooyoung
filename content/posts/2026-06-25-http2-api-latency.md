모니터링 대시보드는 1초마다 CPU, 메모리, GPU, 스토리지, 네트워크 등 API 7개를 동시에 부른다. 백엔드에서는 API 하나가 10ms 안쪽이라고 했는데, 프론트에서 찍어 보면 한 사이클이 45ms 정도 걸렸다. 어디서 시간이 새는지 하나씩 확인해 봤다.

## 측정 방법

프론트에 사이클마다 시간을 찍는 로거를 붙였다.

```
[Perf] ── 새 사이클 ──
  API 요청 시작        [+  0.10 ms]
  모든 API 응답 완료   [+ 30.00 ms]
  1. cpu/usage       | 수신 완료 20.6ms
  2. network/all     | 수신 완료 21.5ms
  ...
  7. storage/all     | 수신 완료 26.9ms
  전체 API 호출 수: 7, 응답 데이터 총량: 9056 bytes
```

크롬 개발자 도구의 네트워크 탭에서는 **프로토콜** 열을 켜 두면 각 요청이 `http/1.1`인지 `h2`인지 볼 수 있다.

## 1. 개발 서버 프록시

개발 모드에서는 Vite 프록시를 거쳐 백엔드로 요청하고 있었다. 프록시를 빼고 직접 요청해 봤다.

| 방식 | 평균 | 표준편차 |
| --- | --- | --- |
| Vite 프록시 경유 | 50.9ms | 18.8 |
| 직접 요청 | 33.9ms | 4.6 |

직접 요청이 빠르고 훨씬 고르게 나왔다. Vite 프록시는 Node 이벤트 루프 하나에서 HMR, 파일 컴파일 같은 일과 같이 돌아가서 흔들림이 커질 수 있다.

다만 양쪽 다 5~6 사이클뿐이라 확실하다고 하기엔 샘플이 적었다. 측정 시점의 백엔드 부하나 네트워크 상태도 달랐을 수 있다. 그리고 운영 환경에는 Vite 프록시가 없으니, 개발 모드 숫자로 운영 성능을 판단하면 안 된다는 것도 같이 배웠다.

## 2. 백엔드 측정과 프론트 측정이 다른 이유

curl로 7개를 동시에 호출해 보면 대부분 5~20ms였다.

```bash
for url in cpu/usage cpu/temperature cpu/wattage system-memory gpu/all network/all storage/all; do
  (
    t=$(curl -o /dev/null -s -w "%{time_total}" "$API_BASE/$url")
    echo "$url : $(awk "BEGIN {printf \"%.2f\", $t * 1000}")ms"
  ) &
done
wait
```

프론트는 브라우저에서 요청이 출발해서 응답을 받아 파싱하기까지를 재고, 백엔드는 핸들러 안의 처리 시간만 잰다. 측정 범위가 다르니 숫자가 다를 수밖에 없다. 백엔드 로그를 보니 요청들이 **같은 몇 개의 연결 포트**를 돌려 쓰고 있었고, "대기 시간 + API 처리 시간"을 더하니 프론트에서 잰 값과 비슷해졌다.

## 3. HTTP/1.1의 연결 수 제한

브라우저는 HTTP/1.1로 같은 출처(origin)에 **동시에 6개**까지만 연결한다. API는 7개라서, 하나는 앞의 요청이 끝날 때까지 기다렸다가 출발한다. 매 사이클마다 그 하나만큼 늦어지는 셈이다.

## 4. HTTP/2로 바꿔 보기

HTTP/2는 연결 하나로 여러 요청을 동시에 주고받는다(멀티플렉싱). 연결 수 제한에 걸리지 않는다.

HTTP/2를 쓰려면

- 백엔드가 HTTP/2를 지원해야 한다. FastAPI를 띄우던 uvicorn은 HTTP/1.1만 지원해서 **hypercorn**으로 실행했다.
- 브라우저는 HTTP/2를 **TLS(HTTPS) 위에서만** 쓴다. 인증서를 붙여서 HTTPS로 바꾸면 브라우저가 알아서 h2로 연결한다.

```bash
hypercorn main:app --bind 0.0.0.0:8443 --certfile cert.pem --keyfile key.pem
```

30사이클씩 비교한 결과다.

| 항목 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 첫 사이클: API 완료 | 85.5ms | 64.7ms |
| 첫 사이클: 렌더 완료 | 102.7ms | 76.8ms |
| 이후 사이클: API 완료 | 27~35ms | 26~31ms |
| 이후 사이클: 렌더 완료 | 51~65ms | 45~53ms |

- **첫 로딩**에서 차이가 가장 컸다. 연결 하나로 7개를 한 번에 받으니까.
- 연결이 맺어진 뒤에는 API 완료 시간 자체는 비슷했다.
- 대신 HTTP/2는 7개 응답이 거의 동시에 도착해서 사이클마다 시간이 **고르게** 나왔고, HTTP/1.1은 사이클이 쌓일수록 렌더 완료 시간이 들쭉날쭉해졌다.

여러 차트를 1초마다 한꺼번에 갱신하는 대시보드에서는 평균보다 이 **균일함**이 체감에 더 중요했다.

## 5. gzip 압축은 오히려 손해

응답 크기를 줄이면 빨라질까 싶어서 gzip도 켜 봤는데, 압축을 끈 쪽이 가장 고르게 나왔다.

- 응답 7개를 다 합쳐도 9KB 남짓이다. 그중 몇 개는 100바이트도 안 된다.
- 1KB 미만의 응답은 압축해도 어차피 TCP 패킷 하나에 들어간다. 줄어드는 게 없고 압축 계산만 늘어난다.
- 6KB짜리도 압축하면 패킷 5개가 2개로 줄지만, 내부망처럼 빠른 네트워크에서는 그 차이가 마이크로초 단위라 거의 의미가 없다.

압축은 느린 외부망에서 큰 응답을 보낼 때 효과가 있다. 그래서 보통 nginx에서도 `gzip_min_length 1024;`처럼 작은 응답은 압축하지 않게 설정한다.

## 정리

- 프론트와 백엔드는 재는 범위가 다르다. 숫자가 다르면 측정 방법부터 맞춘다.
- 개발 서버 프록시는 운영과 다르다. 성능은 운영과 같은 경로로 잰다.
- HTTP/1.1에서는 같은 출처로 동시에 6개까지만 요청이 나간다. 동시에 부르는 API가 많으면 HTTP/2(HTTPS 필요)가 유리하다.
- 작은 응답에 gzip은 손해다.
- 가장 확실한 개선은 **요청 수 자체를 줄이는 것**이다. 다음에는 대시보드용 API 7개를 하나로 합친 엔드포인트를 만들어 볼 생각이다.
